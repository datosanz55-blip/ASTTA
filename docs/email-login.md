# Подключение входа по почте

Вход по почте подготовлен, но по умолчанию выключен. Пока SMTP не настроен и `EMAIL_LOGIN_ENABLED=0`, кнопки входа и привязки почты скрыты. Telegram продолжает работать.

## Как это работает для покупателя

- Новый покупатель открывает профиль → «Войти по почте» → вводит адрес и согласие → получает шестизначный код → вводит его на сайте. Аккаунт создаётся только после подтверждения. Пароля нет.
- Уже есть покупки через Telegram: сначала войти через Telegram, открыть профиль → «Мои данные» → «Привязать почту», подтвердить код. Затем любой из двух способов открывает один и тот же аккаунт с заказами и избранным.
- Если сначала создать отдельный аккаунт по почте, автоматически объединять его с другим аккаунтом Telegram сайт не будет. По совпадению адреса, имени или контакта аккаунты не объединяются.
- В Telegram Mini App сам вход остаётся через Telegram; привязать почту можно из профиля. По почте затем входят в обычной вкладке сайта.
- Подготовлены вход и первичная привязка одного адреса. Самостоятельная смена/отвязка подтверждённой почты, привязка Telegram к отдельно созданному почтовому аккаунту, объединение разных аккаунтов, Google и СМС не реализованы.
- Это письма для входа, а не рассылка статусов заказов: email-покупатель смотрит статусы в профиле. Telegram-уведомления остаются у аккаунтов с Telegram.

## Что нужно от владельца

1. Выбрать провайдера почты или транзакционных писем с SMTP и создать отправителя `login@astta.ru` (название ящика можно другое). Отдельный почтовый сервер на VPS для этого не нужен.
2. Подтвердить домен в панели провайдера. Добавить выданные им DNS-записи для отправки: SPF, DKIM; DMARC — по инструкции провайдера. Для полноценного почтового ящика провайдер также выдаст MX-записи. Значения записей зависят от выбранного сервиса, их нельзя угадать заранее. Не меняйте A/CNAME сайта; при существующем SPF не создавайте второй конкурирующий SPF, согласуйте запись с провайдером.
3. Получить адрес SMTP-сервера, порт, логин и SMTP-пароль/пароль приложения. Уточнить, разрешены ли автоматические письма с кодами и какие лимиты отправки. Пароль хранить только в `infra/.env`, не в GitHub и не в переписке.

## Настройки сервера

После слияния PR с этой функцией открыть в Termius:

```bash
cd /opt/astta
nano infra/.env
```

Добавить настройки, подставив данные своего провайдера:

```dotenv
EMAIL_LOGIN_ENABLED=0
EMAIL_HOST=smtp.provider.example
EMAIL_PORT=587
EMAIL_HOST_USER=login@astta.ru
EMAIL_HOST_PASSWORD=SMTP_PASSWORD_FROM_PROVIDER
EMAIL_USE_TLS=1
EMAIL_USE_SSL=0
DEFAULT_FROM_EMAIL=ASTTA <login@astta.ru>
EMAIL_LOGIN_DAILY_LIMIT=1000
```

Порт 587 обычно использует STARTTLS (`TLS=1`, `SSL=0`). Если провайдер требует порт 465 с SSL/TLS с начала соединения: `EMAIL_PORT=465`, `EMAIL_USE_TLS=0`, `EMAIL_USE_SSL=1`. Одновременно включать обе опции нельзя. Это стандартные [SMTP-настройки Django](https://docs.djangoproject.com/en/5.2/topics/email/); фактические значения даёт провайдер.

Обновить приложение (скрипт сам применяет миграции):

```bash
cd /opt/astta && bash infra/update.sh
```

Нужны три новые миграции: таблицы подтверждённых адресов и запросов кода, а также расширение контакта заказа/заявки до 254 символов для почтовых адресов. Существующие пользователи и заказы сохраняются. Как перед любым обновлением схемы, используйте штатную резервную копию БД.

## Проверка и включение

Отправить обычное тестовое письмо на собственный адрес (замените адрес в конце):

```bash
cd /opt/astta
docker compose -f infra/docker-compose.yml --env-file infra/.env exec backend python manage.py sendtestemail your-address@example.ru
```

Проверить входящие и «Спам». Успешная команда означает, что SMTP принял письмо; она не гарантирует попадание во входящие. Если письмо не пришло, проверить домен отправителя, DNS, журнал отправок провайдера, SMTP-пароль и доступ VPS к нужному порту. Журнал приложения:

```bash
docker compose -f infra/docker-compose.yml --env-file infra/.env logs --tail=100 backend
```

Когда письмо доходит, в `infra/.env` изменить `EMAIL_LOGIN_ENABLED=1` и применить:

```bash
cd /opt/astta
docker compose -f infra/docker-compose.yml --env-file infra/.env up -d backend worker beat
```

Обновить сайт. Проверить вход на свою почту, выход и повторный вход. Затем на существующем Telegram-аккаунте привязать другую свою почту и убедиться, что вход по ней показывает тот же профиль и заказы. Тестировать адрес, который ещё не принадлежит другому аккаунту.

Для отключения: вернуть `EMAIL_LOGIN_ENABLED=0` и повторить `up -d backend worker beat`. Подтверждённые адреса останутся в БД.

## Защита и обслуживание

- Код действует 10 минут, максимум 5 неверных попыток. После успешной проверки повторно не используется. В БД хранится HMAC, исходный код в API и журнал не выводится.
- Запрос входа привязан к браузерной сессии; привязка адреса — к уже вошедшему покупателю. Есть CSRF-проверки. Код не даёт входа сотрудникам, суперпользователям и отключённым аккаунтам.
- Повторная отправка: не чаще раза в минуту; до 6 запросов на адрес в часовом окне, до 10 с IP в час; проверка кодов — до 30 запросов с IP в час. Общий дневной лимит задаётся `EMAIL_LOGIN_DAILY_LIMIT`. В проде лимиты используют общий Redis.
- Удаление запросов кода старше суток выполняется раз в сутки через Celery Beat; поэтому запись может находиться в рабочей БД до двух суток. Ручной запуск: `python manage.py cleanup_email_codes` внутри backend-контейнера. Подтверждённые адреса эта команда не удаляет. Исторические резервные копии имеют свой срок хранения.
- Поле «Подтверждённая почта для входа» видно в карточке пользователя в админке только для чтения. Простое редактирование обычного User.email не выдаёт доступ к аккаунту.
- До включения указать фактического почтового провайдера в черновиках политики и согласия. Имя оператора и остальные незаполненные реквизиты требуют данных владельца.

API: `POST /api/auth/email/request` (`email`, `purpose: login|link`, `consent`) → `challenge_id`; `POST /api/auth/email/verify` (`challenge_id`, `code`, `purpose`) → профиль. `GET /api/site` возвращает `email_login`; это признак конфигурации, а не проверка доставки.
